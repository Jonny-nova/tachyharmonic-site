## Controlled £30 live validation — completed 28 September 2026

Jonathan authorized one real payment/refund test and completed the card step himself. An unguessable temporary token gate was deployed and verified first: public and wrong-token booking calls returned 404, while a private call reached the still-disabled service. The production Worker then temporarily used `PRIVATE_LIVE_TEST=true`, `BOOKING_ENABLED=true`, and `ALLOW_LIVE_PAYMENTS=true`; the Stripe webhook was enabled. No public frontend or custom domain route was opened. The booking used a 15 October 2026, 11:00–12:00 BST slot, outside the initial 14-day statutory period, so no early-performance request was needed.

- The private production availability read consulted the live Google calendars and offered the £30 slot. One durable hold and one live Stripe Checkout Session were created. Stripe showed exactly £30.00 paid, `livemode=true`, with Checkout and payment metadata correlated to the same internal booking ID. The signed `checkout.session.completed` delivery returned HTTP 200.
- The production backend advanced from paid pending to confirmed. Independent Google Calendar API read found exactly one correlated active event with the correct date/time, duration, attendee, description and Meet link. The same link appeared in the canonical booking state. Resend marked the actual confirmation to the intended recipient Delivered, with matching appointment/Meet details.
- The confirmed event blocked the slot. A single controlled cancellation moved the booking through cancellation pending to canceled, then initiated one full £30 refund. Stripe's own payment page showed the £30 payment reversed and the refund succeeded; its `refund.created` and `refund.updated` webhook deliveries returned HTTP 200. Customer bank posting may take additional days. The dashboard also showed a separate £0.65 merchant processing fee, not a deduction from the customer's £30 refund.
- Independent Google read found zero active events with this booking correlation after cancellation. The original slot became available again. Resend marked both the cancellation and refund-initiated messages Delivered. The backend had no pending recovery jobs. One PaymentIntent, one refund ID and no duplicate correlated Calendar event were observed; no further charge or refund was attempted.
- Booking was disabled before closing the webhook. The ordinary production config restored `BOOKING_ENABLED=false` and `ALLOW_LIVE_PAYMENTS=false`; the webhook destination was disabled. The temporary token secret was removed from Cloudflare and the owner-only local operator bundle. Public availability returned `booking_unavailable` (503) after restoration. Live Stripe, Google and Resend credentials remain encrypted production secrets.

This tested the private production API plus live Stripe Checkout, Calendar/Meet and email chain. It did not publish or exercise the final public frontend route. Stripe's succeeded refund is provider evidence at the time of readback, not proof of the customer's bank posting date or immunity from any later provider reversal.

## Legal, privacy and operational gate

The separate, initially unchecked early-performance wording is recorded in the durable contract snapshot. The relevant primary sources are the [Consumer Contracts Regulations 2013](https://www.legislation.gov.uk/uksi/2013/3134), [GOV.UK distance-selling guidance](https://www.gov.uk/online-and-distance-selling-for-businesses), and [ICO storage-limitation guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/).
